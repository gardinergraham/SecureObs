# Care Show signup

## Customer flow

- `/show`: select wards, software, modules, monthly/annual billing and up to two show tablets per ward. Create an email/password account and accept the versioned order terms.
- `/show-account`: sign in and save a payment method through Stripe-hosted Checkout **setup mode**. No subscription or payment is created at signup.
- `/show-admin`: an existing SecureObs **super_admin** signs in using staff code/PIN, agrees the implementation date with the customer and proposes it. Notify the customer through your normal contact process; this feature does not send email automatically.
- The customer signs in, reviews the date and charges and explicitly confirms. Confirmation creates future Stripe subscription schedules. The activation date must be at least 24 hours away and within one year.
- Software and selected paid modules charge in full at activation, monthly or annually. Annual pricing includes two free software/module months. The software has **no free trial**.
- Tablets use a separate monthly subscription: six calendar months free from activation, then £37.99 per retained tablet each month. Annual software customers still pay tablet hire monthly.
- After 12 months, both schedules release their subscriptions to continue automatically on the chosen billing cadence. They do not cancel at 12 months.
- The signed `invoice.paid` webhook provisions the organisation/wards. A paid customer can then choose a six-digit manager PIN in their show account and receive their staff code for the app and existing desktop portal. Saving a payment method or visiting a success URL never grants clinical access.

## Deployment

Deploy **both** the website (Vercel) and backend (Railway). Website-only deployment will not work.

1. Apply migration `053_care_show_orders.sql` through the existing backend migration runner. The backend's existing `start` command runs migrations.
2. Keep `PUBLIC_WEBSITE_URL=https://secure-obs.com` and the existing production Stripe key, webhook secret and configured plan/module/tablet price IDs. The existing key needs Checkout, Customers, SetupIntents (read), Prices (read), Subscription Schedules, Subscriptions and Invoices access. Prefer a restricted key with the necessary permissions. Never expose a key in website files.
3. Ensure the Stripe endpoint `/api/billing/webhook` receives `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, and `customer.subscription.deleted`. It must receive events generated by API-created schedules as well as Checkout. The existing webhook handler now stores its receipt only after successful processing, so a crashed attempt can be retried.
4. Confirm that Stripe account verification, payouts, customer payment/authentication emails and failed-payment recovery are configured. No account settings were changed while building this feature.
5. SecureObs is currently being registered; no limited-company status or registration number is asserted. Review `website/show-terms.html` before publication, including the contracting legal supplier identity, initial commitment, renewals, tablet returns and the relationship to your service/data-processing agreement. The page records the offer agreed in this task; it is not a legal review. No VAT is displayed or collected by this flow. Future tax registration requires an explicit reviewed update, not just changing the catalogue toggle.
6. Run the sandbox checks below before accepting real orders. Do not use the live account or real payment details for testing.

## Validation performed locally

- Backend TypeScript build.
- `node backend/tests/care-show.mjs`: quote validation, monthly/annual amounts, tablet caps, calendar dates, renewal schedule shape, crash recovery, account authentication, setup-only checkout, activation prerequisites, webhook ownership/status checks, administrator guard, confirmed scheduling and manager creation.
- Existing package-pricing and checkout suites.
- Browser pricing interaction, phone-width layout inspection, and a local simulated customer walkthrough: sign-in → date confirmation → manager setup. This walkthrough used a separate localhost fixture API, not Stripe or the production backend.

Stripe and database calls in the route tests are simulated. These checks do **not** establish that production credentials, database permissions, webhook configuration, email delivery or Stripe's real scheduler work. No live customers, schedules, charges or deployments were created.

## Required sandbox run

Use a separate Stripe sandbox with matching test prices, a disposable database and the new migration. Set the API configuration accordingly. Serve a test copy of the website pointed at that backend; do not send test forms to the production Railway URL.

1. Register monthly Essential + one module + two tablets. Save a test card and verify that signup creates no invoice/subscription.
2. Propose a date, confirm it as the customer, and inspect the two future schedules. Repeat confirmation: there must still be only one software and one tablet schedule.
3. Repeat for annual software and no tablets. Confirm full annual software price at activation and no tablet schedule.
4. Advance a Stripe test clock (or use dedicated test fixtures) to activation: verify one software invoice, correct amount, paid-only organisation/ward provisioning, and manager login. Use authentication-required and failed-card fixtures too.
5. Advance six calendar months: check the first monthly tablet invoice and unaffected software cadence. Confirm renewal continues after month 12.
6. Replay webhooks and retry after simulated failures: no duplicate organisations, staff or schedules. Confirm an invalid signature never changes an order.
7. Record all tablets returned before month seven; verify no future tablet charges. Repeat after month 12 to verify cancellation of the released subscription.

## Operations and recovery

- Customer order summaries can be printed from their account. Terms version, selected quote and acceptance/confirmation timestamps are retained in PostgreSQL.
- Keep a copy of each published terms version; never overwrite the meaning of an existing version identifier.
- An existing email signs in rather than creating a second order. For a forgotten password, verify the customer's identity through your established contact process before an administrator resets the stored PBKDF2 hash. Invalidate `care_show_sessions` for that order. Self-service email recovery is not included.
- Orders and package quantities are immutable in this first signup flow. Agree amendments separately and reconcile Stripe and ward allocations; do not edit database selections alone. Partial tablet returns need a Stripe quantity adjustment; the admin button confirms **all** tablets returned and stops only tablet hire.
- The software billing report remains the software subscription ledger. Tablet schedules are separate Stripe subscriptions identified by `metadata.showOrderId` and `metadata.kind=tablets`; their invoice failure events do not suspend software.
- If scheduling fails partway, the customer can retry confirmation. Matching schedules are found by customer/order/kind before creation, including beyond Stripe's idempotency-key retention window. If the agreed date has passed, investigate existing schedules before changing dates or retrying; do not create a duplicate schedule.
- Cancellation/changes to software still use your existing support process and Stripe Dashboard. Review schedules as well as subscriptions, including both software and tablet hire. Do not cancel software immediately when notice is for the end of the initial term.
- Setup sessions can be resumed from the account after cancellation. After activation is confirmed, payment-method changes go through the existing billing support process.
